# Status

A fastify service acting as a router for internal homelab health checks, consumed mostly by Site. Built and run by Gateway, publicly reverse-proxied by Caddy at `status.dl.imetrical.com`. Its own compose entry flags it as legacy, expected to be retired once replaced by live monitoring services (hasura/ipfs) — active, but not core.

## Language

**Tedcheck**:
Checks a MySQL `watt` table for missing samples, at day/week/hour granularity. The `watt` readings come from **Ted** (see Missing) — Daniel's home power monitor ("The Energy Detective").

**Logcheck**:
Checks Scrobblecast digest logs for gaps by querying **Loggly** (see Cloud accounts) — Scrobblecast's 3 peer instances publish "checkpoint" events there, which is also how they coordinate synchronization with each other (hence the name). They publish the same events to NATS too, not just Loggly.

**Note — build risk**: deployed via Gateway's docker-compose (`build: ../../packages/status/`), so the risk is less "does it run on my current Node" and more "does its Dockerfile's pinned base image still build" — unverified. Worth checking before any migration to a new monorepo structure.

**Note — actually called, not vestigial**: `packages/site/content/index.mdx` (Site's homepage) renders `Summary`/`Tedcheck`/`ScrobbleCheck` from `FetchedStatuses.js`, polling `/api/version` (10s), `/api/tedcheck` (60s), `/api/logcheck` (60s) live in-browser. `scripts/bash/qcic-sh.sh` hits the same three directly. Of `/api/version`'s response, only `data.stamp` is actually rendered (as a "Last Fetched at" freshness indicator) — `hostname`/`version` are fetched but unused, so despite the name this endpoint functions as a liveness/freshness ping, not a version check.

**Note — v2 port (see [[ADR-0002]])**: `status` is the first package being ported to the new `v2/` Bun-monorepo subtree, chosen for its simplicity (no Deprecated-package dependency, unlike `site`) and to prove Bun-in-production before committing `site`'s larger rebuild to it. Phase 1 is a faithful, behavior-frozen lift — same 3 endpoints, same data shapes, name stays `status` — onto: TypeScript + ESM, Hono (replacing Fastify — chosen over Elysia for its smoother Fastify migration and Node fallback, since Bun-in-prod is unproven here), and `prosodio`'s conventions (`bun test`, ESLint+Prettier+markdownlint, `bun run ci`). Deployment shape is unchanged — Gateway still builds from source via docker-compose, same public URL, same gitignored-secret-mount pattern — only the `build:` context repoints to `v2/` once ready; switchover timing is deliberately TBD pending review of what depends on the endpoint. The official `oven/bun` multi-stage Dockerfile pattern (non-root `bun` user, digest-pinned base) replaces the current `dumb-init`-wrapped Node image; the actual requirement is rapid/clean shutdown, not `dumb-init` specifically — Bun's own signal handling needs verifying before deciding whether an init wrapper is still needed. E2E testing may need to grow into exercising the built Docker artifact itself, not just source — flagged as an implementation-time question.

Phase 2 (not yet started) evolves `status` into something that actively monitors Ted/Scrobblecast and peer instances rather than passively proxying — that's also when a rename becomes worth considering. It includes a concrete, distinct decision: **Logcheck's source of truth: Loggly → NATS.** Scrobblecast already publishes checkpoint events to both, so this is a real swap candidate, not a redesign — but not a drop-in one, since Loggly's search API gives free time-range querying that NATS core pub/sub doesn't (would need JetStream or similar for replay). This is specifically about what Logcheck itself treats as source of truth, independent of how any client consumes Status's API — a separate concern from `site`'s own `/wayfinder` decision about how central NATS should be to the *client*. Resolving one doesn't require resolving the other.
